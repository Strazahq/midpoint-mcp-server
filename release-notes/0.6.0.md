This release makes Get access offer what midPoint's own request rules allow each person, shows midPoint's reason when it refuses a change, and takes request fields from midPoint's schema.

## What's new

- **Get access follows midPoint's request rules.** midPoint can let different people request different roles, for different people, as different relations. The server now works this out from the same rules midPoint checks (the `#assign` authorizations of the person's roles):
  - "Request for" lists yourself and the people your rules let you request for, such as your reports;
  - the catalog lists only the roles your rules allow for that person;
  - a relation other than member, such as "Approve requests for it", appears only where a rule names it;
  - each role has "Why you can request this", naming the rule;
  - fields and dates follow what the rule allows.

  midPoint still decides when you send the request. A live test against midPoint 4.10.3 (73 real requests) found that every prediction the preview was sure of matched midPoint. The test is in the repository, so you can run it against your own midPoint. New tool `list_request_targets`; `request_role` takes `relation`.
- **midPoint's reason on refusals.** When midPoint refuses a change, the person sees why. Examples are a policy rule's own message ("Requests for this role need a justification") and a missing permission. Before, they saw "unexpected status 409". HTTP 409 has its own error code, `refused`.
- **Request fields from midPoint's schema.** The request dialog offers every assignment field in midPoint's schema, as midPoint's own Request access page does: choice lists from an enumeration or a lookup table, fields with several values, whole and decimal numbers, and required marks.
- **Approvers see what a request carried:** every field, labelled as midPoint labels it, and the comment the requester typed in midPoint's own Request access page.
- **The demo** reads like a chat app, every action in it completes, and it shows the request rules. Try it at [strazahq.github.io/midpoint-mcp-server](https://strazahq.github.io/midpoint-mcp-server/).

## Fixed

- My requests listed every request twice, once as "an item you can't see in midPoint". midPoint files a request as an "operation request" case with an approval case under it, and the server listed both. Each request is now listed once.
- Searching roles by text (`list_requestable_roles` with `query`) failed with HTTP 500 on midPoint 4.10.3.

## Breaking changes

- The settings `requests.formItems` and `requests.justificationItem` are ignored, with a warning at startup. Request fields come from midPoint's schema instead.
- On work items and cases, `justification` becomes `requestDetails` (every field the request carries) and `requesterComment`. `server.requestReason` is removed.

## Before you upgrade a shared deployment

`examples/role-mcp-rs-service.xml` gains reads for the service account. They cover definitions only, not anyone's data:

- `rest-3#getObjects` and `rest-3#getExtensionSchema`, plus `model-3#read` on schemas and lookup tables and `model-3#getExtensionSchema`: the request fields;
- `model-3#read` on a few items of roles, orgs, services and archetypes (`read-request-rules`): the request rules.

Without the request-field reads the dialog has no fields, and the server says so at startup. Without `read-request-rules`, Get access lists the roles flagged requestable, as before. Both were verified on midPoint 4.10.3. To let approvers see the requester's comment, `docs/authorization.md` has the read to grant them.

## midPoint versions

This release supports midPoint 4.10. Everything in it was verified against midPoint 4.10.3. midPoint 4.8, 4.9 and 4.11 are not tested and may not work. The README section "midPoint versions" lists the version-sensitive parts.
