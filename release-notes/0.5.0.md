This release makes the four views readable, puts names next to IDs everywhere a person approves a change, and adds self-service, operator and group-approval tools.

## What's new

- **Readable views.** Requests to approve, Get access, My requests and My team's access are redesigned after two independent reviews:
  - colour means status only;
  - people show as initials and roles, teams and accounts as icons;
  - each status is a pill with a word;
  - facts read as label and value ("Asked by", "How long", "Why you");
  - every action is a real button;
  - full screen shows a table of rows.

  My team's access says where each role came from ("approved by you") and when it ends.
- **Names you can check before you allow a change.** Every write tool takes the midPoint name of the user, role, task or system next to its ID. A chat app that asks "Allow this tool?" then shows "carol" and "End user", not two IDs. The server refuses a name that doesn't match its ID before writing anything. Results also start with names, for example "Would assign role End user to Carol Jensen (carol).", with the IDs on a separate line.
- **Approvals offered to a group.** When an approval step names a group, any member can claim the request in the inbox and then decide it, or release it back to the group. New tools `claim_work_item` and `release_work_item`.
- **New tools:**
  - `get_my_access`: your own roles, with who requested and approved each.
  - `list_expiring_access`: access of you and your team that ends soon.
  - `list_recent_errors`: what failed in the last hours. It checks failed tasks, accounts with failed operations, broken accounts, systems that are down, and audit errors where allowed.
  - `list_tasks`, `get_task`, `run_task`, `suspend_task`, `resume_task` and `test_resource` for operators.
- `get_user_assignments` reports where each assignment came from: who created, requested and approved it, and the approval comment.

## Breaking changes

- `decide_work_item`, `cancel_request`, `assign_role` and `unassign_role` require `userName` and `roleName`. `recompute_user`, `enable_user` and `disable_user` require `userName`. `request_role` requires `roleName`, and also `userName` with `userOid`. These are midPoint's unique `name` values, such as a login, not display names. The views send them already.
- The text of write results changed: names first, then `Case:` and `Request:` lines. Clients that parse that text need updating. The structured results are unchanged.

## Before you upgrade a shared deployment

- `examples/role-mcp-rs-service.xml` is now the complete role for the service account:
  - the REST entry actions, including `#claimWorkItem`, `#releaseWorkItem` and `#cancelCase`;
  - `#proxy`;
  - one read authorization, so the server can find the user behind a token.

  It holds no other rights over data. Every call runs on the person's own midPoint rights, and people need no REST rights of their own. Verified on midPoint 4.10.3.
- If the service account still holds a personal-mode role with broad rights over data, such as `examples/role-mcp-direct-service.xml`, remove it. In shared mode those rights only let the account change data by itself.
- Withdrawing a request also needs `model-3#cancelCase` on the person's own cases. To show requests offered to a group, approvers need a read authorization for those items. midPoint's stock roles have neither. `docs/authorization.md` has both as XML.

## midPoint versions

This release supports midPoint 4.10. Everything in it was verified against midPoint 4.10.3. midPoint 4.8, 4.9 and 4.11 are not tested and may not work. The README section "midPoint versions" lists the version-sensitive parts.
